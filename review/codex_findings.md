Findings:
- [high] 1. Prospective scoring trusts flags instead of enforcing the registered deadline (scripts/score_live.py:39-44)
  score_live never checks logged_utc or when forecasts were committed. Its only eligibility checks are prospective=True and date>=2026-10-01. An in-memory reproduction accepted an October forecast logged 122 days later. This is a demonstrated validation gap, not evidence that current forecasts were backdated. A misflagged or recovered retrospective row can enter the primary Brier estimate after its outcome is known. The September correction fixes those specific rows but leaves the general failure intact.
  Recommendation: Validate 0<=logged_utc-decision_date<=15 days, reject inconsistent flags and duplicate dates, and verify timely forecast commitment against an auditable publication record. Add late-row rejection tests. No new paid calls are needed.
- [high] 2. Historical prompt changes can prevent logging every subsequent month (scripts/run_live.py:142-154)
  log_model classifies every live month before loading the existing log. Revised inputs or a changed prompt create new cache keys for already logged dates; a differing historical answer then raises SystemExit before any new rows are saved. A mocked reproduction classified both June and October, then aborted on June without logging October. Because run_live.main processes models sequentially, the exception also prevents later models from logging. This can turn an old input discrepancy into missing prospective forecasts despite obtaining fresh answers.
  Recommendation: Load existing logs before classification and call only unlogged dates. Freeze each logged input snapshot; validate its hash separately without requesting another forecast. Isolate model failures so other models can complete. No paid calls are needed to fix or test this.
- [medium] 3. Rerunning a parse-failed live month cannot recover it (scripts/run_live.py:142-157)
  run_live always uses run=0 with the same retry limit. run_task caches invalid answers under attempts 0, 1 and 2, then reuses all three on subsequent executions. A fake-cache reproduction ran classification twice: both executions made zero provider calls, recorded three parse failures and left the month failed. The instruction to rerun within the prospective window therefore works for uncached transport failures, but not exhausted parse failures. Such months remain missing even if the provider would now return valid JSON.
  Recommendation: Introduce an explicitly registered, persistent continuation of retry attempts for unlogged months, preserving failed records and prohibiting retries after a valid forecast is logged. Test recovery from exhausted cached parse failures. Testing requires no paid calls; actual recovery would require new calls.
- [medium] 4. Model changes are logged but never reported as the promised break (scripts/score_live.py:37-51)
  The Phase 10 registration promises that a change in model_returned is reported as a break. run_live stores the identifier, but score_live groups all rows under the configured model name and neither checks nor reports identifier changes. A provider returning a new model version will silently contribute to the same Brier estimate and checkpoint CI. This makes the reported series a mixture of models. A backend replacement retaining the same returned identifier is additionally undetectable with the recorded metadata.
  Recommendation: Detect returned-model changes, emit explicit break records, and predefine whether checkpoints restart or are stratified by version. Pin immutable provider versions where available and disclose undetectable same-ID replacements. No new paid calls are needed.
- [medium] 5. Counterfactual sensitivity does not rule out historical recall generally (README.md:59-62)
  README says the result 'rules out pure recall'. The primary metric measures probability movement after editing inputs, but no edited-snapshot date probe establishes that the model still identifies the original month. A historical recognizer could interpret the edited fingerprint as a different episode and recall a different outcome; it would also move more than the unedited re-ask baseline. This is an identification limitation, not evidence that this mechanism actually occurred. The reported positive TV-minus-noise intervals establish sensitivity to these edits, not the claimed exclusion of recall.
  Recommendation: Limit the claim to rejecting answers invariant to the selected edits, and update nb05 consistently. That correction needs no paid calls. Stronger identification would require a newly registered experiment addressing whether edited prompts change historical recognition.
